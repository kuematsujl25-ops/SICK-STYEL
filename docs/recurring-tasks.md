# 毎朝8時の継続タスク

通常の「タスク」と「担当タスク」の追加画面で、単発／継続（毎日8時）を選びます。継続の場合、期限欄は開始日になります。開始日以降、毎朝08:00 Asia/Tokyoに当日期限の新しい未完了タスクを作ります。今日の8時以降に登録した場合は次の確認（通常15分以内）で当日分を作ります。担当・優先度・メモ・関連先も引き継ぎます。

各画面の「継続タスク設定」から内容を編集し、停止／再開できます。編集は次回生成分から反映されます。停止していた日は再開時に埋めず、今日以降を再開します。開始日と出力先は変更不可です。変更したい場合は旧設定を停止し、新しい設定を追加してください。過去の完了・未完了・ゴミ箱はそのまま残ります。

開いているタスク／担当タスク／ダッシュボードは既存の1分ごとの取得とフォーカス復帰時に最新状態を反映します。編集中のダイアログや入力欄を上書きしません。更新が競合した場合は再読み込みが必要です。

## 保存と再実行

既存workspace文書にrecurringTasks配列を追加し、旧データでは空配列に補完します。DBスキーマ変更はありません。生成タスクにはrecurringIdとoccurrenceDateを保存し、テンプレートのnextDateと同じrevision条件付きUPDATEでまとめて確定します。競合時は最新データを読み直し、最大4回試行します。失敗してもカーソルだけが進むことはありません。生成済みタスクの削除・完了変更後も同じ日を再生成しません。

日付計算は端末のタイムゾーンに依存しません。朝8時を過ぎた日まで処理し、障害後は1テンプレートにつき1実行最大31日分を補完します。長い停止からの復旧は次回実行で続きます。停止テンプレートは対象外です。既存の配列上限10,000件に達するとバッチ全体を保存せず失敗します。履歴を自動削除する処理はありません。運用でバックアップ・容量管理を行ってください。

通常保存では旧クライアントによるテンプレート削除やカーソルの巻き戻しを拒否します。バックアップ復元は専用の統合処理です。現在存在する継続設定と生成済み履歴（完了・未完了・論理削除を含む）を優先して保持し、バックアップの不足分を補います。同じ生成日が重複する場合は現在の記録を優先します。通常の単発データは従来どおりバックアップで置き換えます。

バックアップだけにある継続設定は、過去の開始日を許容して「停止」で取り込みます。次回生成日は「バックアップのカーソル」「復元翌日」「復元した最終生成日の翌日」の最大値にします。明示的に再開するまで生成せず、復元だけで過去日を再生成しません。現在も存在するテンプレートの設定は復元で巻き戻しません。開始日・出力先の通常編集制限は維持します。異なる履歴のID衝突、テンプレートの出力先衝突、統合後の件数上限超過は復元全体を拒否し、履歴を切り捨てません。

自動生成が有効な場合、管理画面に「10,000件上限」または「予定より15分以上遅延」の警告を表示します。サーバー時刻と保存済みカーソルから判定するため、DBへのエラー記録書き込みに依存しません。次の取得（通常1分または更新ボタン）で反映します。これは画面内監視で、Push通知ではありません。DB自体が読めない場合は既存の通信エラー表示となります。31日ずつ補完している場合も遅延警告は残ります。

## 安全停止と旧版への復帰

第一選択は現在のコードを保持して `RECURRING_TASKS_ENABLED=false` にすることです。通常のタスク管理は継続でき、保存形式も保持されます。ただし全体フラグの停止中も有効テンプレートのカーソルは進まないため、再有効化時に未生成日を補完します。停止期間を補完したくない場合はテンプレートを停止・再開してください。

旧版8528bf2の通常保存はrecurringTasksを落とすため、書き込み可能なまま戻してはいけません。旧版へ戻す必要がある場合の手順は次のとおりです。

1. 本人承認のもと、現在版で `RECURRING_TASKS_ENABLED=false` と `MAINTENANCE_MODE=true` を設定し、APIが503になることを確認する。外部の手動DB書込やAI runnerも実行しない。
2. D1全体SQL・現在Version配分・設定・cronを非公開領域へ保存し、SQLをローカル復元して整合性を確認する。preflightのバックアップに加え、この停止時点のバックアップを確保する。
3. 記録済み旧Versionへコードを戻す。旧VersionのVariablesにMAINTENANCE_MODE=trueが確実に適用されていることを確認してから切り替える。旧Versionが保守falseのままなら、そのVersionへ直接切り替えず、旧ソースを保守trueとして用意する。APIのGET/PUTが503になることを直後に再確認する。旧版のscheduledも保守trueで即終了する。DB・cronは復元や削除をしない。
4. 修正版を通常手順で反映し、保守状態のままworkspaceの継続設定・履歴・カーソルをバックアップと照合する。機能フラグfalseを維持してMAINTENANCE_MODEを解除し、ログイン・読み取り・保存互換を確認する。その後、承認範囲で自動生成を再有効化する。

この手順の旧版保守APIと新コードへの復帰は `tests/recurring-recovery.test.js` で旧コミットの実Worker bundleと同じ永続ローカルD1を用いて検証します。旧版で通常編集を再開する手順ではありません。旧版のまま編集を再開したい場合は、別途保存互換パッチが必要です。DBの全体巻き戻しは他の業務更新を失うため、このコード復旧手順では行いません。
