# Amazon Ads履歴の容量対策

現在値と最大30件の履歴を同じ文書に持つ旧方式では、現在値が上限以内でも履歴との合計が1,500,000バイトを超えると完了結果を保存できず、同じpendingレポートの再取得を繰り返していた。

保存時はUTF-8のシリアライズサイズを計測し、1,400,000バイトを超える間、または履歴が30件を超える間、古い履歴を同じD1の`ss_documents`内へ保全する。文書名は`amazonads-reports-history/`と内容ハッシュ。本文は`{profileId,snapshot}`で、snapshot内の日時・reportId・対象期間・変更前の全行を保持する。履歴を削除・外部送信しない。現在文書の`historyArchived`は保全件数であり、全件の参照配列を追加して再び現在文書を肥大化させない。

保全文書のINSERTは現在文書のrevision一致を条件とし、CAS更新と同じstore.transaction（D1 batch）で実行する。並行更新に負けた処理は保全文書を作らず、途中の保存失敗では双方がロールバックされる。完了結果は別オブジェクトで組み立て、保存失敗時も元の現在値・履歴・pendingジョブを維持して同じレポートを再取得できる。

保全文書と現在文書それぞれに1,500,000バイトの上限を維持する。現在値だけで上限を超えた場合は容量エラーとし、実績を切り捨てない。履歴保全によりDBの総使用量は増えるため、FreeのDB総容量や書込上限に達すれば保存を停止する。自動削除や有料プランへの切替はしない。容量増大時は運用者がバックアップと保存方針を確認する。

復元・調査は権限のある管理者がD1バックアップから`name LIKE 'amazonads-reports-history/%'`の文書を取り出し、現在文書のhistoryと合わせてprofileId/reportId/atで確認する。公開APIや画面へ生の保全履歴を追加していない。既存のD1全体SQLバックアップに含まれる。スキーマ移行は不要。

旧コードは保全文書を参照しないが削除もしない。コードのRollbackで履歴が消えることはない。ただし旧コードで広告同期を再開すると元の容量問題が再発し得るので、Rollback後は自動同期の運用状態を確認すること。

検証は架空データのみ。容量境界を超える複数回同期、全履歴の内容保持、トランザクション途中失敗と再試行、競合時の無変更、現在値自体の容量超過、30件超の保全を確認する。実広告APIは呼ばない。
