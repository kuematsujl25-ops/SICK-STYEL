# Instagram営業集計・ローカル試作

## 起動と検証

`node tools/instagram-preview/server.js` → http://127.0.0.1:4178

依存パッケージ不要。合成サンプル → 候補を検査 → 確認チェック → 試算台帳へ追加。
`npm test` は既存ビルドと全テスト。単体は `node --test tests/instagram-sales-preview.test.js`。

## 完成範囲と未完成範囲

これは収集後の候補検査・集計を検証する独立UIであり、Instagramの自動収集機能ではない。
既存アプリのログイン、Instagramログイン、OAuthは実装・変更しない。実DMの取得精度は未検証。
通常のブラウザ閲覧は既読状態を変える場合がある。収集開始前にログイン中の所有者を確認し、指定と違えば停止する。
ユーザーが対象アカウントを指定した後、少数の会話で日時・方向・相手・先頭履歴・案内の根拠が通常UIから読めるか検証する必要がある。
Cookie/token抽出、非公開API、無人巡回、送信、自動名寄せは実装していない。

試作は合成データ用。本番データの投入・永続保存・公開・デプロイには別承認が必要。
サーバーは127.0.0.1のみ、GETで固定4ファイルを配信する。ブラウザから候補データを送信しない。
外部スクリプトなし。localStorage、IndexedDB、DB、ファイル保存なし。再読込で台帳・候補が消える。
候補JSONも生本文もログに出さない。JSONの追加フィールドは拒否する。ただし許可フィールドの誤用まで個人情報検出はできないため、本文を入力しない。
ユーザーのブラウザ拡張機能によるページ閲覧はアプリ側では制御できない。

## データ契約

`sample.json` が合成例。上限100候補/バッチ、UI入力200KB。
所有者、取得元（manual / browser_observation）、取得日時、確認対象期間（JST）、部分確認のみを保持。
各候補に相手handle、種類、活動日（JST、曖昧ならnull）、方向、先頭確認、初回送信確認、根拠コード、検証済みフラグ、未確認理由、任意の既存営業先IDを保持。
`browser_observation` は取得者の申告でありブラウザによる署名証明ではない。
本文や抜粋は保持しない。日時は日単位。曜日だけの表示や年が不明な表示から日付を推測しない。
handleは不変のInstagram IDではない。改名・再利用の可能性があり、実運用前に本人確認・対応表が必要。
初回DMは履歴先頭および最初のoutboundの確認が必須。途中履歴だけでは新規と計上しない。
返信・案内は各月の活動相手数。メッセージ通数ではなく所有者＋相手で重複排除する。
Zoomという語があるだけでは案内としない。明確な送信側の招待を確認できる時だけ計上。

## 既存KPIとの境界

既存 `salesKpiRecords`、履歴取消、過去案件、cron、Amazon、AI分析には変更しない。
既存KPIは初回返信月を数える。今回は月内返信のユニーク相手数なので合算しない。
初回DM月コホートも別出力とし、観測済みの後続活動のみ追跡する。率の確定表示はしない。
候補台帳はappend-only、同一所有者＋相手＋種類＋活動日で再取込を無視。
初回DM日または同じ活動の営業先対応が競合したらバッチ全体を停止する。
取消済み履歴を復活させるような本番連携は存在しない。Zoom案内をappointmentに変換しない。
未確認候補は現在のプレビューに理由付きで表示し、台帳には追加しない。別バッチ検査時にプレビューは置換される。永続的な訂正・保留台帳は次段階。
